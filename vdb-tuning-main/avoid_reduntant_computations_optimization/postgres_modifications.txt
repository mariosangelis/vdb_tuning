

------------------------------------------------------------Compilation Time-----------------------------------------------------------

We have 2 stages, the compilation time and the execution time. During the compilation time, each expression must be compiled. We have the query
SELECT key FROM image_data ORDER BY embedding<=>q LIMIT ;

ExecInitIndexScan [nodeIndexScan.c]
    -> ExecAssignScanProjectionInfo

        //This is gonna compile all the expressions including select,where, order by
        -> ExecBuildProjectionInfo [execExpr.c]
            ->For each expression, call the ExecInitExprRec in order to build the steps

    //This is only for the expressions included in the order by
    -> ExecInitExprList(node->indexorderbyorig, (PlanState *) indexstate);
        -> Call ExecInitExpr for each node of the orderbyoriginal



We have multiple sources of compilation (nodes). One is the index scan, the other one is Limit.

Each node has a planstate->plan->targetlist.
This target list contains all the expressions that we need to compile. Each target/expression can be an Op expression, a var, a const etc...

------------Scan Node-----------

First of all, the scan node needs to compile the expressions for the projection and that's why it calls the ExecBuildProjectionInfo passing the planstate->plan->targetlist.
Thus, each expression is compiled further and at the end we have a list of steps (scratches) that will run during execution.

Each step contains:
    int opCode,
    /* where to store the result of this step */
	Datum	   *resvalue;
	bool	   *resnull;
    ...

In our case, since we dont have qual, we have 2 expressions.
The first one is the select key (safe variable) so this triggers directly a EEOP_ASSIGN_SCAN_VAR without compiling the expression further. Thus, the first step will be EEOP_ASSIGN_SCAN_VAR

The other expression is the expression "embedding <=> q" which is a T_OpExpr (operand) expression and this compiles further.

The OP expression consists of a Const (q) and a T_Var (embedding).
So the T_Var will be the second step (EEOP_SCAN_VAR)
Then the EEOP_FUNCEXPR_STRICT will be the third step.
And finally, when the OP expression compilation returns to ExecBuildProjectionInfo, we will have another step: EEOP_ASSIGN_TMP that will copy the result to scratch.d.assign_tmp.resultnum

Now, another important step is the decomposison of each tuple into individual column values (tts_values[]).
For this, we need to copy the attributes we need for the expressions to the tts_values of the tupleslot. Thus, we need another step that comes first of all the other generated by the expression compilation and this step is EEOP_SCAN_FETCHSOME. It fetches all the attributes until the max attrnum we need (embedding) in our case and it copies the data from memory
to the TupleTableSlot at runtime.

IMPORTANT: Toasted values are not gonna be detoasted during EEOP_SCAN_FETCHSOME, but only when we access the individual toasted field for example using EEOP_SCAN_VAR.

Thus, for one more time, the indexscan node will call the ExecBuildProjectionInfo giving as an argument all the targetist. This will trigger the compilation of each expression in the target list and we will have a list of step objects. Finally, the indexscan node will call the ExecInitExprList only for the order by expressions.



------------------------------------------------------------Execution Time-----------------------------------------------------------


ExecIndexScan
    ->  ExecScan(&node->ss,IndexNextWithReorder). [execScan.c] So IndexNextWithReorder is the access method
        -> ExecScanFetch [execScan.c]
            -> IndexNextWithReorder [nodeIndexScan.c]
                -> index_get_next_slot
                    -> tid = index_getnext_tid(scan, direction);
                    -> index_fetch_heap(scan, slot)
        -> ExecProj [executor.h]
            -> ExecInterpExpr [execExprInterp.c]



The access method for our index is IndexNextWithReorder and its passed as an argument to ExecScan.
Exec Scan is our main function. This is the "one tuple at a time model". In a loop, it calls the IndexNextWithReorder (via ExecScanFetch) and it receives a slot as a reply.
The slot is a TupleTableSlot struct. Under the hood, IndexNextWithReorder calls index_get_next_slot which calls the ivfflatgettuple function from our index.
That's how postgres is connected with the ivfflat index. The tid of the next tuple is received through the index and then the actual page where this tid resides is fetched from the disk.

index_fetch_heap function is used to fetch the actual heap tuple given a TID (tuple ID) returned by the index scan. It:
Retrieves the tuple from the heap (i.e., the base table),
Stores the full tuple in the TupleTableSlot (i.e., slot->tts_tuple),
But does not immediately decompose the tuple into individual column values (tts_values[]).

Then, execScan calls the execProj function which calls the ExecInterpExpr function. ExecInterpExpr executes all the steps of the projection state.
For the query SELECT key FROM image_data ORDER BY embedding<=>q LIMIT 3;

Without any modifications, the steps are the following:
1) CASE_EEOP_SCAN_FETCHSOME fetch attributes 1-8 (until embedding attribute)
2) CASE_EEOP_ASSIGN_SCAN_VAR Copy attribute 1 (key) to result column
3) EEOP_SCAN_VAR Copy attribute 8(embedding) to the temp result slot
4) CASE_EEOP_FUNCEXPR_STRICT: execute function
5) CASE_EEOP_ASSIGN_TMP: copy result to
6) CASE_EEOP_DONE: end

As we know, steps 3-6 are reduntant. So, we want to modify the compilation phase and ignore those steps based on some conditions.
We want to have something like
1) CASE_EEOP_SCAN_FETCHSOME fetch attributes 1-8 (until embedding attribute)
2) CASE_EEOP_ASSIGN_SCAN_VAR Copy attribute 1 (key) to result column
3) CASE_EEOP_DONE: end

We need to modify the expression compilation only during the ExecBuildProjectionInfo phase.
Thus, we go to the ExecInitExprRec function that compiles each expression and we focus in T_OpExpr

case T_OpExpr:{
            OpExpr     *op = (OpExpr *) node;

            elog(INFO, "🔶 ExecInitExprRec: OpExpr found (probably embeddings <=> param)");
            ListCell *lc;
            foreach(lc, op->args)
            {
                    Node *arg = lfirst(lc);
                    elog(INFO, "  ↪️ OpExpr Arg nodeTag: %d", nodeTag(arg));
            }

            elog(INFO, "  op->opfuncid: %d", op->opfuncid);


            if (state->optimize_for_topk_search &&  IsA(state->parent, IndexScanState)){
                    IndexScan *plan = (IndexScan *) ((PlanState *) state->parent)->plan;

                    bool skip=false;
                    ListCell *lc2;
                    foreach(lc2, plan->indexorderby){
                            Node *node = (Node *) lfirst(lc2);

                            if (IsA(node, OpExpr)){
                                    OpExpr *node_op = (OpExpr *) node;

                                    if(SemanticAnalysis(op,node_op)){
                                            //if (tle_op->opno == node_op->opno && list_length(tle_op->args)==list_length(node_op->args)){
                                            skip=true;
                                            elog(INFO, "📌  ✅ Skipping OpExpr because it is covered by indexorderby inside compilation");
                                            break;  // Skip compiling this OpExpr into evaluation steps
                                    }
                            }
                    }
                    if(skip){
                            if(state->current_tle->resjunk){
                                    state->optimize_for_topk_search_eliminate_expression=true;
                                    break;
                            }
                            else{
                                    scratch.opcode = EEOP_FETCH_INDEX_DISTANCE;
                                    ExprEvalPushStep(state, &scratch);
                                    break;
                            }
                    }
            }

            ExecInitFunc(&scratch, node,op->args, op->opfuncid, op->inputcollid, state);
            ExprEvalPushStep(state, &scratch);
            break;
}


We dont want to skip for any other phase except ExecBuildProjectionInfo. Thats why we need to add the state->optimize_for_topk_search flag.
ExecBuildProjectionInfo will set is as true state->optimize_for_topk_search=true;
So, we add also this bool optimize_for_topk_search flag to the ExprState struct [execNodes.h];

Then we check if the parent state is an index scan and it has an expression that is covered by index (thats why we run a semantic analysis), then we can skip if the expression is not used in the select (resjunk==true) or copy the result of this expression directly from the index.
In case we skip because its resjunk, we need to inform the ExecBuildProjectionInfo so that is does not add the last step to the scratch.
And this happens as follows: We set the optimize_for_topk_search_eliminate_expression flag as true to the state object again so that the ExecBuildProjectionInfo knows.

So for the query SELECT key FROM image_data ORDER BY embedding<=>q LIMIT 3, instead of this:

1) CASE_EEOP_SCAN_FETCHSOME fetch attributes 1-8 (until embedding attribute)
2) CASE_EEOP_ASSIGN_SCAN_VAR Copy attribute 1 (key) to result column
3) EEOP_SCAN_VAR Copy attribute 8(embedding) to the temp result slot
4) CASE_EEOP_FUNCEXPR_STRICT: execute function
5) CASE_EEOP_ASSIGN_TMP: copy result to
6) CASE_EEOP_DONE: end

we have this:

1) CASE_EEOP_SCAN_FETCHSOME fetch attributes 1-8 (until embedding attribute)
2) CASE_EEOP_ASSIGN_SCAN_VAR Copy attribute 1 (key) to result column
3) CASE_EEOP_DONE: end


So we entirely skip the OpExpr.

SELECT key, embedding<=>q as distance  FROM image_data ORDER BY distance LIMIT 3

what about this query?
Distance is already computed in the index, so we can copy it, we dont need to calculate it again every time.
How can we do that?
In this case, embedding<=>q is not resjunk, so we create a custom op called EEOP_FETCH_INDEX_DISTANCE.
This step will copy the distance from the index directly to the temp storage and then, the ExecBuildProjectionInfo will add a CASE_EEOP_ASSIGN_TMP to copy the result to the result slot

So, if we go inside execExprInterp.c, we add this custom op
EEO_CASE(EEOP_FETCH_INDEX_DISTANCE)
{
        *op->resvalue = scanslot->tts_custom_value;
        *op->resnull = scanslot->tts_custom_isnull;
        EEO_NEXT();
}
which is copying the distance from the index to the temp storage of this execution step.
After that, the CASE_EEOP_ASSIGN_TMP will assign this value to the resultslot

EEO_CASE(EEOP_ASSIGN_TMP)
{
        int resultnum = op->d.assign_tmp.resultnum;

        Assert(resultnum >= 0 && resultnum < resultslot->tts_tupleDescriptor->natts);
        resultslot->tts_values[resultnum] = state->resvalue;
        resultslot->tts_isnull[resultnum] = state->resnull;

        EEO_NEXT();
}
-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------

Of course this is gonna work with even more complex expressions

SELECT key, 100* (10+ (embedding<=>q)) FROM image_data ORDER BY embedding<=>q LIMIT 3

The embedding<=>q is computed and it can be returned directly from the index, we dont need to calculate it again during the projection, so we can store it in temp storage
and let the op function (10+embedding<=>q) to reuse it from there without computing it again.
