1M data, IVFFLAT index
shared_buffers, work_maintenance_memory

In IVFFLAT search, we need at least K*dim*float_size work_mem to sort, but this is small.

In IVFFLAT build, we need more work_maintenance_memory to sort, but this is small.
If we have more work_maintenance_memory, then all the detoasted vectors are stored in memory and the loading to pages is faster.
BUT: not a lot, its a compute bound probelm. mOST OF THE TIME is used to run kmeans and for eacj tuple to compute the closest centroid

For examle: 1M data, build index with 1000 clusters, we spend:

 with 10GB of work_maintenance_memory

Kmeans: 45-50 sec
detoast:                       9
compute_nearest_centroid:      132
save_slot_to_heap:             0.76

sort based on centroids:       0.06

load to pages:                 15.8


 with 300MB (minimum required to run kmeans) of work_maintenance_memory

Kmeans: 45-50 sec
detoast:                       9
compute_nearest_centroid:      135
save_slot_to_heap:             0.76

sort based on centroids:       0.52

load to pages:                 16.5



Parallelization is not used from implementation
